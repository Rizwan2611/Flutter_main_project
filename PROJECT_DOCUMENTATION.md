# ExhibitGuide — Project Documentation

## 1. Project overview

ExhibitGuide is a Flutter mobile museum companion. It lets visitors discover artworks, search and filter the gallery, view detailed exhibit notes, build a favorite collection, browse a museum map, manage preferences, and access support information.

The interface is based on the supplied **Museum App** Figma design. The current implementation is mobile-first and supports an offline-first data model: the app remains usable with local preferences and favorites, while an optional backend synchronizes account data.

## 2. Main capabilities

| Area | What it does |
| --- | --- |
| Splash and onboarding | Introduces ExhibitGuide and guides a visitor into the app. |
| Authentication | Supports local demo sign-in by default and backend signup/login when an API address is configured. |
| Gallery | Searches, filters, and displays a curated exhibit grid. |
| Exhibit details | Shows artwork information, location, opening information, zoomable image, and favorite action. |
| Favorites | Persists saved exhibit IDs and shows the visitor collection. |
| Profile | Shows locally stored user name/email and links to map, settings, help, and about. |
| Settings | Persists notification, offline-download, and dark-mode toggles. |
| Museum map | Shows a simple illustrated floor map and highlighted exhibition area. |
| Help and About | Provides FAQs, contact details, and application information. |

## 3. Figma → IDE workflow used

1. The Figma link was inspected through the Figma connection.
2. The design-to-code guidance was loaded before requesting a design frame.
3. Figma page metadata identified the screen frames, including `splash-welcome`, gallery, exhibit detail, favorites, sign-up, profile settings, museum map, and help support.
4. The `splash-welcome` frame was requested as the initial implementation target. Its hierarchy established the full-bleed image, 55% dark overlay, centered wordmark, clay action button, and bottom indicator.
5. The original Figma splash artwork was downloaded into `assets/images/splash-welcome.png` and registered through the existing `assets/images/` declaration in `pubspec.yaml`.
6. Flutter-native layout widgets were used instead of copying the generated React/Tailwind reference. This keeps the screen responsive and interactive on mobile.
7. The Figma screens were then translated into the existing Flutter flow, including gallery, detail, profile, map, settings, and support routes.

## 5. Data storage design

### On-device storage

`shared_preferences` saves simple offline data in the operating system's private app storage:

- Android uses SharedPreferences.
- iOS uses UserDefaults.

The data is not kept in a visible Dart file. It survives app restarts but is normally cleared if the app is uninstalled or its data is cleared.

| Local key | Value |
| --- | --- |
| `visitor_name` | Visitor display name |
| `visitor_email` | Visitor email |
| `session_token` | Optional backend session token |
| `favorite_exhibit_ids` | List of saved exhibit IDs |
| `notifications_enabled` | Notification preference |
| `offline_downloads_enabled` | Offline-content preference |
| `dark_mode_enabled` | Theme preference |

The curated exhibit text is packaged as Dart constants in `main.dart`. Current gallery/onboarding images use network URLs except for the locally bundled Figma splash artwork; bundle additional gallery images for a completely image-offline release.

### Backend storage

The optional Node backend writes to `backend/data/userdata.json` at runtime. It stores:

- user ID, name, email, creation date;
- a salted `scrypt` password hash (never a plain password);
- favorite exhibit IDs;
- notification, offline, and dark-mode preferences;
- hashed seven-day session tokens.

`userdata.json` is intentionally in `backend/.gitignore`. Never commit user records, tokens, passwords, or real secrets.

## 6. Backend API

| Method | Endpoint | Authentication | Description |
| --- | --- | --- | --- |
| GET | `/health` | No | Checks that the API is running. |
| POST | `/api/auth/signup` | No | Creates an account; requires name, email, and password of at least 8 characters. |
| POST | `/api/auth/login` | No | Validates email/password and returns a token. |
| GET | `/api/me` | Bearer token | Returns the signed-in user’s public profile. |
| GET/PUT | `/api/me/favorites` | Bearer token | Reads/replaces favorite exhibit IDs. |
| GET/PUT | `/api/me/preferences` | Bearer token | Reads/updates toggle settings. |

After login, Flutter saves the returned token locally. Favorites and settings are then synchronized to the API while retaining the local values as an offline fallback.

## 7. Running the project

### Flutter app

```bash
flutter pub get
flutter run
```

Without an API address, the app operates in local demo mode. The account name/email, favorites, and toggle settings remain on the device.

### Backend-enabled app

Run the backend in a separate terminal:

```bash
cd backend
npm start
```

Then launch Flutter with an API address:

```bash
# macOS, Windows, Linux, or iOS simulator
flutter run --dart-define=API_BASE_URL=http://localhost:3000

# Android emulator
flutter run --dart-define=API_BASE_URL=http://10.0.2.2:3000
```

For a real phone, use the computer’s LAN IP and ensure the phone can reach it. Use HTTPS, not plain HTTP, for any deployment outside a controlled development network.

## 9. Security and production recommendations

The included backend is suitable for a student project, demonstration, or local prototype. A production release should add:

1. HTTPS behind a reverse proxy.
2. PostgreSQL, Firebase, Supabase, or another managed database instead of a JSON file.
3. Refresh-token rotation and secure device token storage (for example, `flutter_secure_storage`).
4. Rate limiting, account lockout, password reset email, and email verification.
5. Input validation schema, structured logging, monitoring, backups, and CORS restricted to trusted origins.
6. A real OAuth implementation for the Google and Apple buttons.
